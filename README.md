# 선물 선택 연구 · 새 스키마 7.0.0

## 현재 연구 흐름

참가자 코드 입력은 없습니다. 첫 시작 시 서버가 등록번호와 ID를 발급합니다. P01은 **선물 주는 사람**, P02는 **선물 받는 사람**이라는 역할 표기입니다. 같은 참가자가 두 역할을 수행하며, 각 역할에서 A·B·C·D 네 조건을 체험합니다. 두 역할의 데이터는 trial별로 분리됩니다. 관계 친밀도 조작은 없습니다.

한 기기로 다른 사람을 진행할 때는 시작 화면에서 역할을 고른 뒤 **새 참가자로 시작**을 선택합니다. 이전 사람이 진행 중이어도 새 ID를 발급하며, 이전 사람의 기록은 지우지 않고 미완료(`withdrawn`)로 남깁니다. 같은 사람의 두 번째 역할을 이어갈 때는 새 참가자 옵션을 선택하지 않습니다.

| 조건 | 후보 세 개 | 최종 선물 |
| --- | --- | --- |
| A | 사람이 Agent와 대화해 하나씩 요청·확정 | 사람이 하나를 선택하고 이유 작성 |
| B | Agent가 세 개를 한 번에 제시 | 사람이 하나를 선택하고 이유 작성 |
| C | 사람이 Agent와 대화해 하나씩 요청·확정 | Agent가 셋 중 하나를 확정하고 이유 제시 |
| D | Agent가 세 개를 한 번에 제시 | Agent가 셋 중 하나를 확정하고 이유 제시 |

조건 순서만 5명 단위로 배정합니다. 각 5명 블록에는 네 가지 Williams 순서가 한 번씩 들어가고, 다섯 번째 순서는 다음 블록마다 순환합니다. 참가자 수 상한은 없습니다. 등록번호 30이나 50은 운영자가 정할 수 있고 코드에 고정되지 않습니다. 현재 종이 프로필 코드는 등록번호를 따라 R1–R4 중 하나를 선택해 한 참가자의 네 조건에서 동일하게 유지합니다. 이 프로필 회전은 조건 순서의 별도 균형 요인이 아닙니다.

시작 화면은 친구 목록 → 종이 프로필 확인 → 선물하기 → 세로 채팅입니다. **종이로 제공하는 것은 선물 받을 사람의 프로필 자극물**입니다. 실제 상품 후보 카드, 비교, 대화와 결과는 앱에 표시합니다. 수혜자 역할에는 연구자가 검토한 구성 시나리오를 보여주며 실제 증여자–수혜자 짝의 행동으로 표현하지 않습니다.

후보 3개는 **조건당 하나의 후보 단계**에서 만들며, 후보 하나마다 시간을 다시 세지 않습니다. 후보 단계와 최종 단계는 각각 서버 기준 유효 노출 **60–180초**입니다. 탭을 벗어나거나 연결이 끊기면 다음 heartbeat에서 노출 누적을 중지합니다. 180초가 되면 미완료 행동과 `timeout`을 기록합니다. 참가자는 그 조건을 `skipped`로 남기고 다음 조건 코드를 입력해 계속할 수 있으며, 누락된 후보·최종 선택·설문을 만들어 채우지 않습니다. 한 역할의 4조건 노출은 정상 완료 시 8–24분, 두 역할은 16–48분입니다. 종이 설문과 전환 시간은 별도입니다.

첫째–넷째 조건의 진입 코드는 기존에 정한 400, 590, 1234, 5905이며 **체험 순서**에 적용합니다. 코드 원문은 클라이언트 번들이나 로그에 저장되지 않습니다. 이는 참가자 ID 입력과 별개로 연구자가 조건 전환 시 전달하는 코드입니다.

## Supabase: 새 테이블만 사용

**데이터 삭제 주의:** 아래 첫 SQL은 `public`의 기존 연구 테이블과 상품 데이터를 삭제합니다. 이전 기록이 필요하면 먼저 Supabase에서 별도 백업하세요. 이 저장소에서는 SQL을 실행하지 않았습니다.

1. SQL Editor에서 [study-fresh.sql](supabase/study-fresh.sql)을 실행합니다. 이 파일은 기존 연구 테이블을 지우고 `study_people`, `study_products`, `study_stimuli`, `study_trials`, `study_messages`, `study_events` **6개만** 만듭니다. 각 함수와 접근 제한도 생성합니다.
   이미 위 파일로 운영 중이라면 다시 실행하지 마세요. 아직 적용하지 않았다면 [study-timeout-continue.sql](supabase/study-timeout-continue.sql)을 실행하고, 이어서 [study-new-participant.sql](supabase/study-new-participant.sql)을 실행하세요. 두 파일은 기존 기록을 유지하면서 각각 시간초과 후 다음 조건 진행 및 새 참가자 시작을 추가합니다.
2. [study-products.sql](supabase/study-products.sql)을 실행합니다. 사용자가 제공한 Walmart CSV에서 선택된 12개 승인 상품의 독립 스냅샷입니다. 연구 가격은 과거 CSV 시점의 USD에 1,350원을 적용하고 100원 단위로 반올림한 값이며 현재 판매가가 아닙니다. 이는 **프로필당 3개 상품만 승인**된 상태이므로 순차 후보 재요청의 선택 폭은 제한적입니다. 연구자가 더 넓은 상품 풀을 원하면 검토·승인한 행을 추가해야 합니다.
3. [study-stimuli-draft.sql](supabase/study-stimuli-draft.sql)은 선택 실행합니다. 4개 프로필×4조건에 대한 **미승인 초안** 16개를 만듭니다. 연구자가 대화 문구, 최종 상품, 상품 통제, 노출 순서를 직접 검토·수정해야 합니다. 미승인 상태에서는 수혜자 역할이 시작되지 않습니다. 검토가 끝난 뒤에만 [study-approve-stimuli.sql](supabase/study-approve-stimuli.sql)을 실행합니다.
4. Vercel 서버 환경변수에 `SUPABASE_URL`, 서비스 역할 키, `ANTHROPIC_API_KEY`, 실제 접근 가능한 `ANTHROPIC_MODEL`, `ADMIN_PASSWORD`를 설정하고 배포합니다. 브라우저용 `NEXT_PUBLIC_` 변수에 비밀 키를 넣지 않습니다.

구버전 설치 SQL과 실행 경로는 저장소에서 제거했습니다. `study-fresh.sql`은 신규 설치 전용이며 운영 DB에 다시 실행하면 데이터가 삭제됩니다.

## 자료 구조와 분석

- `study_people`: 자동 등록 ID, 역할 순서, 5명 블록, 네 조건의 순서. 참가자 수 상한 없음.
- `study_products`: 검토된 Walmart 상품 사실·이미지·연구용 가격.
- `study_stimuli`: 수혜자용 연구자 검토 시나리오. 같은 프로필의 A–D에서 후보·가격·최종 상품을 동일하게 고정.
- `study_trials`: 사람×역할×조건, 과업 수행 주체, 후보·결과 스냅샷, 서버 유효 노출, 시간초과·종이 설문 완료.
- `study_messages`: 화면 대화의 순서, 발신자와 실제/Agent/구성 시나리오 출처.
- `study_events`: 서버 시각, 클라이언트 시각, 역할·조건·단계·행위자·출처·멱등성 키를 포함한 원시 행동 기록.

관리자 화면은 여섯 원시 테이블과 `study_metrics.csv`를 분리해 내보냅니다. 지표 계산 규칙: 단계 유효시간은 `study_trials`의 서버 누적값, 후보 상세 체류시간은 화면이 보이고 연결된 동안의 `candidate_dwell.duration_ms` 합, 재방문 수는 상품별 전체 열람 수에서 최초 1회를 뺀 합입니다. 프롬프트 수정·선택 변경·시간초과·이탈·재접속·오류는 해당 이벤트의 개수입니다. Agent 처리시간은 저장된 응답 이벤트의 `latency_ms` 합입니다. 측정되지 않은 체류시간·처리시간은 빈 값으로 내보냅니다. 구성 시나리오의 행동은 `origin='scripted'`이므로 실제 수혜자의 입력으로 세지 않습니다.

```bash
npm run typecheck
npm test
npm run build
```

현재 코드의 타입 검사·단위 테스트·빌드는 통과했습니다. **실제 Supabase 초기화, Claude 호출, 두 역할 전체 파일럿, 59/60/180초 경계와 브라우저 화면 검증은 미실행**입니다. SQL·상품·자극물 적용 뒤 연구자가 실제 세션으로 확인해야 합니다. 후보 재요청을 충분히 허용하려면 프로필당 승인 상품을 3개보다 늘리는 연구자 결정이 필요합니다.
