# 선물 선택 연구 시스템 · 연구 버전 6.0.0

## 현재 설계

새 버전은 친밀도 요인을 사용하지 않습니다. 시작 화면의 **P01은 선물 주는 사람, P02는 선물 받는 사람**이라는 역할 표시이며 참가자 코드가 아닙니다. 참가자는 코드를 입력하지 않습니다. 첫 역할 시작 시 서버가 연구 대상 ID와 역할별 ID를 만들고, 같은 브라우저의 서명된 세션으로 두 번째 역할을 이어갑니다. 30명은 5명씩 6개 등록 블록으로 자동 배정하며 조건 순서와 프로필 회전은 독립적으로 균형을 맞춥니다. 역할 시작 순서는 연구자가 참가자에게 안내하며, 먼저 선택한 역할이 해당 참가자의 첫 역할로 고정됩니다.

선물 받을 사람의 프로필은 연구자가 종이로 제공합니다. 앱에는 대화, 실제 DB 상품 후보 카드, 비교, 최종 선택 또는 Agent 확정 결과가 표시됩니다. 선물 받는 사람 역할에서 화면에 표시되는 선물 주는 사람의 행동은 검토·동결한 연구 시나리오로 기록하며 실제 짝 참가자의 행동이라고 표현하지 않습니다.

| 화면 조건 | 기존 condition_id | 후보 세 개 구성 | 최종 선물 확정 |
| --- | --- | --- | --- |
| A | C1 | 참가자가 구체적 요청을 세 번 작성하고, 매번 상품 한 개를 검토·확정 | 참가자 + 직접 작성한 선택 이유 |
| B | C3 | Agent가 승인 상품 풀에서 세 개를 한 번에 생성 | 참가자 + 직접 작성한 선택 이유 |
| C | C2 | A와 동일한 순차 요청·후보 확정 | Agent가 후보 세 개 중 하나와 근거를 확정 |
| D | C4 | Agent가 승인 상품 풀에서 세 개를 한 번에 생성 | Agent가 후보 세 개 중 하나와 근거를 확정 |

A/C의 포괄적 위임 문구는 Claude를 부르기 전에 서버가 거부합니다. 구체적인 사람 프로필 근거와 이번 후보의 방향이 확인되어야 Claude가 승인된 상품 풀에서 하나를 반환합니다. 같은 입력의 네트워크 재시도는 멱등성 키로 중복 생성을 막고, 새로 작성한 동일 문장은 새 요청으로 저장됩니다. B/D는 서버의 일괄 생성 경로만 사용합니다. A/B의 사람 선택은 이유를 직접 작성해야 하며, C/D의 Agent 최종 결과는 수정할 수 없습니다.

각 조건은 `candidates`와 `decision` 두 단계입니다. 단계별 유효 노출은 60–180초이고, 화면 숨김·연결 중단 시간은 제외합니다. 참가자가 다음 버튼을 눌러야 단계가 이동합니다. 180초에 끝나면 미완료·시간초과로 기록하고 사람의 후보 확정이나 최종 선택을 대신 만들지 않습니다. 역할당 실험 노출은 8–24분이며, 두 역할 합계는 16–48분입니다. 조건별 종이 설문 8회와 전환 코드 입력 시간은 별도입니다.

## Supabase 적용과 로컬 준비

1. Supabase SQL Editor에서 [`fresh-v6-install.sql`](supabase/fresh-v6-install.sql) **한 파일만** 실행합니다. 기존 연구 참가자·조건·로그·시나리오 테이블을 삭제하고 새 연구 스키마를 만듭니다. 승인된 Walmart 상품 원본 `public.product_catalog`는 보존합니다. 전체 파일은 하나의 트랜잭션으로 실행되므로 중간 오류 시 초기화도 롤백됩니다. 기존 연구 자료가 필요하면 실행 전에 백업합니다. **이 SQL은 이 저장소에서 실행하지 않았습니다.** 분리된 원본 SQL 파일은 설치 내용 검토용으로 보관합니다.
2. `product_catalog`에 `walmart-2024-08-curated-v2` 버전의 승인 상품이 각 R1v5–R4v5 프로필에 예산 이내로 최소 3개씩 있는지 확인합니다. CSV를 Vercel에 업로드하지 않습니다.
3. `v6_stimuli`에는 프로필 4개×조건 C1–C4, 총 16개의 연구자 검토·동결 시나리오가 필요합니다. 후보 상품 ID·표시 순서·상품 스냅샷·최종 상품은 같은 프로필의 네 조건에서 같아야 합니다. 시나리오 속 선물 주는 사람의 행동은 실제 짝 참가자의 행동이라고 표현하지 않습니다. 이 승인 자극의 실제 연구 콘텐츠는 현재 제공된 파일에 없어 코드가 임의로 만들지 않았습니다. 이 항목을 채우기 전에는 선물 받는 사람 역할의 본실험이 차단됩니다.
4. 프로젝트 루트 `.env.local`에 Supabase 서버 키와 URL을 설정하고, 선물 주는 사람 역할을 운영할 환경에는 서버 전용 `ANTHROPIC_API_KEY`를 설정합니다. Claude 모델 ID는 계정에서 실제로 제공되는 값을 `ANTHROPIC_MODEL`에 설정합니다. 키를 브라우저용 `NEXT_PUBLIC_` 변수로 두지 않습니다.
5. SQL 적용 후 실제 연결을 확인합니다.

```bash
npm run validate:experiment
npm run typecheck
npm test
npm run build
```

`N001`–`N030`은 DB 내부에 자동 발급되는 등록 번호이며 참가자가 입력하지 않습니다. P01/P02는 화면상 역할 표시입니다. 첫 조건 진입과 후속 조건 진입 코드는 연구자가 별도로 전달합니다. 전환 코드 원문은 클라이언트 번들·행동 로그에 기록하지 않습니다.

## 로그와 내보내기

원시 이벤트는 `event_logs`, 화면 대화와 상품 카드 표시는 `trial_messages`, A/C 개별 요청과 Claude 응답 메타데이터는 `v6_candidate_requests`, 단계 노출은 `v6_phase_records`, 최종 선택과 참가자 이유는 `final_selections` 및 `v6_selection_reason_history`, 코드 시도는 `v6_transition_attempts`에 저장됩니다. 새 역할 데이터는 `role_sessions`와 `research_subjects`를 통해 연결됩니다. 수혜자 화면에서 재생한 행동은 `event_origin='scripted'` 및 모의 행위자로 구분합니다.

관리자 CSV는 원시 자료 `event_logs`, `trial_messages`, `v6_candidate_requests`, `v6_phase_records`, `v6_transition_attempts`와 파생 자료 `v6_analysis_ready`를 별도로 제공합니다. 분석 CSV는 후보 요청·수정, Agent 처리시간, 단계 유효 노출, 후보 상세 열람·재방문, 사람 선택시간, 시간초과·이탈·오류를 원시 로그와 구분합니다. 후보 상세 체류시간은 열기/닫기 이벤트가 실제 기록된 경우만 계산하며 미측정 값은 빈 값으로 둡니다.

## 확인 상태

현재 `npm run typecheck`, `npm test`, `npm run build`로 저장소 코드를 확인합니다. Supabase SQL 적용, 승인된 v6 수혜자 시나리오 16개, 실제 Claude 호출, 실제 DB 파일럿, 브라우저 59/60/180초·탭 이탈·새로고침 검증 및 Vercel 배포는 별도 운영 확인이 필요합니다.
