# 선물 선택 연구 · 스키마 7.1.0

## 현재 연구 흐름

연구자가 첫 시작 화면에서 역할별 **참가자 ID**를 입력합니다. 선물 받는 사람은 홀수 `K01`, 선물 주는 사람은 짝수 `K02`처럼 연속된 두 ID가 같은 사람의 한 쌍입니다. 다음 사람은 `K03`/`K04`입니다. `K100` 이상도 쓸 수 있습니다. 화면의 P01과 P02는 각각 선물 주는 사람·받는 사람의 **역할 코드**이며 참가자 ID가 아닙니다. 서버의 자동 등록 순번은 5명 단위 조건 순서 배정에만 사용합니다. 각 역할에서 A·B·C·D 네 조건을 체험하고, 역할과 조건별 기록은 별도 trial에 저장합니다. 관계 친밀도 조작은 없습니다.

한 기기로 다른 사람을 진행할 때는 새 참가자 ID를 입력합니다. 서버가 기존 ID와 다름을 확인하고 새 내부 UUID를 발급하며, 이전 사람의 기록은 지우지 않고 미완료(`withdrawn`)로 남깁니다. 같은 사람의 두 번째 역할을 이어갈 때는 해당 역할의 짝 ID를 입력합니다. 예: K02로 증여자 역할을 마쳤다면 K01로 수혜자 역할을 시작합니다. 기술적 기본키인 UUID는 내부에서만 사용하고, 역할별 K ID를 `study_trials`, `study_messages`, `study_events`의 `participant_number`에 기록하며 `study_people`에는 `giver_number`, `recipient_number`를 함께 저장합니다. `study_people.participant_number`에는 처음 입력한 역할의 K ID가 남습니다.

| 조건 | 후보 세 개 | 최종 선물 |
| --- | --- | --- |
| A | 사람이 Agent와 대화해 하나씩 요청·확정 | 사람이 하나를 선택하고 이유 작성 |
| B | Agent가 세 개를 한 번에 제시 | 사람이 하나를 선택하고 이유 작성 |
| C | 사람이 Agent와 대화해 하나씩 요청·확정 | Agent가 셋 중 하나를 확정하고 이유 제시 |
| D | Agent가 세 개를 한 번에 제시 | Agent가 셋 중 하나를 확정하고 이유 제시 |

조건 순서만 5명 단위로 배정합니다. 각 5명 블록에는 네 가지 Williams 순서가 한 번씩 들어가고, 다섯 번째 순서는 다음 블록마다 순환합니다. 참가자 수 상한은 없습니다. 등록번호 30이나 50은 운영자가 정할 수 있고 코드에 고정되지 않습니다. P01의 종이 프로필 코드는 등록번호를 따라 R1–R4 중 하나를 선택해 한 참가자의 네 조건에서 동일하게 유지합니다. 이 프로필 회전은 조건 순서의 별도 균형 요인이 아닙니다. P02의 R1–R4 코드는 저장 구조의 연결 키로만 사용하며 참가자 화면에 표시하지 않습니다.

시작 화면은 친구 목록 → 프로필 확인 → 선물하기 → 세로 채팅입니다. P01에는 선물 받을 사람의 종이 프로필을 제공합니다. P02에는 **친구 A가 같은 생일 선물을 준비한 네 상황**이라는 공통 이야기를 보여줍니다. P02의 네 조건에는 연구자가 승인한 같은 후보 세 개와 최종 선물 하나를 사용하며, 선택 방법을 나타내는 대화만 조건별로 다릅니다. 상품 카드, 비교, 대화와 결과는 앱에 표시합니다. P02의 행동은 연구자가 구성한 시나리오이며 실제 P01 참가자의 행동으로 표현하지 않습니다.

후보 3개는 **조건당 하나의 후보 단계**에서 만들며, 후보 하나마다 시간을 다시 세지 않습니다. 후보 단계와 최종 단계는 각각 서버 기준 유효 노출 **30–180초**입니다. 탭을 벗어나거나 연결이 끊기면 다음 heartbeat에서 노출 누적을 중지합니다. 180초가 되면 미완료 행동과 `timeout`을 기록합니다. 참가자는 그 조건을 `skipped`로 남기고 다음 조건 코드를 입력해 계속할 수 있으며, 누락된 후보·최종 선택·설문을 만들어 채우지 않습니다. 한 역할의 4조건 노출은 정상 완료 시 최소 4분·최대 24분, 두 역할은 8–48분입니다. 종이 설문과 전환 시간은 별도입니다.

첫째–넷째 조건의 진입 코드는 기존에 정한 400, 590, 1234, 5905이며 **체험 순서**에 적용합니다. 코드 원문은 클라이언트 번들이나 로그에 저장되지 않습니다. 이는 참가자 ID 입력과 별개로 연구자가 조건 전환 시 전달하는 코드입니다.

## Supabase: 새 테이블만 사용

**데이터 삭제 주의:** 아래 첫 SQL은 `public`의 기존 연구 테이블과 상품 데이터를 삭제합니다. 이전 기록이 필요하면 먼저 Supabase에서 별도 백업하세요. 이 저장소에서는 SQL을 실행하지 않았습니다.

1. 새 DB를 만드는 경우에만 SQL Editor에서 [study-fresh.sql](supabase/study-fresh.sql)을 실행합니다. 이 파일은 기존 연구 테이블을 지우고 `study_people`, `study_products`, `study_stimuli`, `study_trials`, `study_messages`, `study_events` **6개만** 만듭니다. 각 함수와 접근 제한도 생성합니다.
   이미 이 여섯 테이블로 운영 중이라면 다시 실행하지 마세요. 참가번호 컬럼이 아직 없다면 [study-participant-number.sql](supabase/study-participant-number.sql)을 먼저 실행하고, 이어서 [study-k-ids-30s.sql](supabase/study-k-ids-30s.sql)을 실행하세요. 이미 참가번호 컬럼을 적용했다면 두 번째 SQL만 실행합니다. 이 SQL은 기존 기록을 보존하면서 새 ID를 K 홀수·짝수 역할별 쌍으로 기록하고 서버 단계 전환 기준을 30초로 바꿉니다. 구버전에서 시간초과 후 다음 조건 기능이 아직 없다면 [study-timeout-continue.sql](supabase/study-timeout-continue.sql)을 먼저 적용하세요. 기존 [study-new-participant.sql](supabase/study-new-participant.sql)은 새 참가자 ID를 받지 않는 예전 RPC를 설치하므로 더 이상 적용하지 마세요.
   지금까지의 파일럿 데이터를 모두 삭제하려면 스키마 SQL 적용 후 [study-reset-test-rows.sql](supabase/study-reset-test-rows.sql)을 별도로 실행합니다. 여섯 테이블의 모든 행이 삭제되며 상품과 P02 승인 자극물도 함께 사라집니다. 실제 연구 데이터가 섞여 있다면 실행 전에 확인하세요.
2. Vercel 서버 환경변수에 `SUPABASE_URL`, 서비스 역할 키, `ANTHROPIC_API_KEY`, 실제 접근 가능한 `ANTHROPIC_MODEL`, `ADMIN_PASSWORD`를 설정하고 배포합니다. Claude Console에서 **Web search**를 활성화합니다. 브라우저용 `NEXT_PUBLIC_` 변수에 비밀 키를 넣지 않습니다.
3. 관리자 화면 `/admin`에서 **웹 검색으로 후보 준비**를 실행합니다. 서버가 Claude의 실시간 웹 검색으로 상품 페이지를 찾고, 상품명·가격·이미지를 직접 확인한 후보 세 개와 최종 선물 하나를 `study_products`와 `study_stimuli`의 **미승인** 16개 행에 저장합니다. 연구자는 상품 사진·가격·출처와 같은 후보·최종 선물 여부를 검토한 뒤 **승인**합니다. 승인 전에는 새 P02 조건을 시작할 수 없습니다. 승인하면 4개 내부 연결 코드 × A–D 모두 같은 후보·최종 선물을 사용합니다.
4. P01은 A·C의 개별 상품 요청과 B·D의 후보 세 개 준비 시마다 Claude 실시간 웹 검색을 사용합니다. 저장된 CSV 상품은 새 추천 경로의 검색 풀에 들어가지 않습니다. 이전에 시작한 trial의 상품 스냅샷은 바꾸지 않습니다.

실시간 웹 검색은 Walmart·Target·Amazon의 상품 페이지로 제한합니다. 서버가 페이지의 구조화된 상품명·이미지·USD 가격을 직접 읽지 못하면 그 상품은 후보에 넣지 않습니다. 판매처가 자동 접근을 막거나 구조화된 가격을 제공하지 않으면 해당 요청은 실패할 수 있습니다. 웹 상품은 검색 당시 정보를 trial에 저장합니다. P01은 참가자마다 상품과 가격이 달라질 수 있으므로 본 실험 전 파일럿에서 이 변동을 검토해야 합니다. P02는 승인한 동일 후보와 최종 선물을 재사용합니다.

이전 설계의 Walmart 적재·P02 고정 초안 SQL은 저장소에서 제거했습니다. 운영 중인 DB에 `study-fresh.sql`을 다시 실행하면 참가자 기록이 삭제됩니다.

구버전 설치 SQL과 실행 경로는 저장소에서 제거했습니다. `study-fresh.sql`은 신규 설치 전용이며 운영 DB에 다시 실행하면 데이터가 삭제됩니다.

## 자료 구조와 분석

- `study_people`: 연구자가 입력한 두 역할 ID(`recipient_number`, `giver_number`), 첫 입력 ID, 내부 UUID, 자동 등록 순번, 역할 순서, 5명 블록, 네 조건의 순서. 참가자 수 상한 없음.
- `study_products`: 서버가 판매 페이지의 구조화된 데이터를 직접 확인한 웹 상품의 이름·가격·이미지·출처. 기존 CSV 상품이 남아 있어도 새 추천에는 사용하지 않습니다. 웹 상품은 `dataset_version`이 `live-web-...`이며, 참가자 trial에 당시의 스냅샷을 저장합니다.
- `study_stimuli`: P02용 연구자 검토 시나리오. 모든 내부 프로필 코드와 A–D에서 후보·가격·최종 상품을 동일하게 고정합니다.
- `study_trials`: 참가번호와 사람×역할×조건, 과업 수행 주체, 후보·결과 스냅샷, 서버 유효 노출, 시간초과·종이 설문 완료.
- `study_messages`: 참가번호와 해당 조건의 대화 순서, 발신자와 실제/Agent/구성 시나리오 출처.
- `study_events`: 참가번호, 서버 시각, 클라이언트 시각, 역할·조건·단계·행위자·출처·멱등성 키를 포함한 원시 행동 기록.

`study_products`와 `study_stimuli`는 여러 사람이 함께 쓰는 상품·시나리오 원본이므로 참가번호를 넣지 않습니다. 참가번호는 네 개의 참가 기록 테이블과 파생 지표 CSV에 포함됩니다. 다음 조건을 열면 화면에는 그 조건의 대화·상품·입력값만 보이며 이전 조건 기록은 DB에 남습니다.

관리자 화면은 여섯 원시 테이블과 `study_metrics.csv`를 분리해 내보냅니다. 지표 계산 규칙: 단계 유효시간은 `study_trials`의 서버 누적값, 후보 상세 체류시간은 화면이 보이고 연결된 동안의 `candidate_dwell.duration_ms` 합, 재방문 수는 상품별 전체 열람 수에서 최초 1회를 뺀 합입니다. 프롬프트 수정·선택 변경·시간초과·이탈·재접속·오류는 해당 이벤트의 개수입니다. Agent 처리시간은 저장된 응답 이벤트의 `latency_ms` 합입니다. 측정되지 않은 체류시간·처리시간은 빈 값으로 내보냅니다. 구성 시나리오의 행동은 `origin='scripted'`이므로 실제 수혜자의 입력으로 세지 않습니다.

## 확인과 운영

```bash
npm run typecheck
npm test
npm run build
```

배포 환경의 Claude Web search와 상품 페이지 접근은 실제 연결 뒤 확인해야 합니다. **실제 Supabase 쓰기, Claude 호출, 두 역할 전체 파일럿, 29/30/180초 경계와 브라우저 화면 검증을 이 저장소 작업만으로 확인했다고 볼 수 없습니다.** 검색 결과가 3개 미만이면 미승인 상태로 남고 연구자에게 오류를 표시합니다.
